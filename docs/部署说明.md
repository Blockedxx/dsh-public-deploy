### 本轮修复的一个真实缺陷

**桥接层错误体格式**：上游异常断开时原本返回裸文本
`bridge upstream error: socket hang up`，被平台网关二次包装成笼统的
`{"code":502,"msg":"bad gateway"}`，丢失真实原因。现已改为结构化 JSON：

```json
{"code":502,"msg":"bridge upstream error",
 "data":{"upstream":"127.0.0.1:13080/api/...","reason":"ECONNRESET","message":"socket hang up"}}
```

同时补齐了响应中途断连收尾（防客户端悬挂）与客户端提前断开时的上游释放（防连接泄漏）。

## 三、架构与数据流

```
┌────────────────────────────────────────────────────────────────┐
│  浏览器                                                         │
│  https://<YOUR-SANDBOX-ID>.app.workbuddy.host/                 │
└───────────────────────────┬────────────────────────────────────┘
                            │ HTTPS (443)
                            ▼
┌────────────────────────────────────────────────────────────────┐
│  腾讯云 CLB  —— TLS 终止                                        │
│  解析示例：lb-xxx.clb.bj-tencentclb.cloud  (49.233.240.214)     │
└───────────────────────────┬────────────────────────────────────┘
                            │ HTTP
                            ▼
┌────────────────────────────────────────────────────────────────┐
│  沙箱网关（CloudStudio Gateway）                                │
│  · 按「子域名中的端口号」路由                                     │
│  · 格式：<PORT>-<SPACE_KEY>.e2b.<REGION>.sandbox.cloudstudio... │
│  · ⚠️ 转发时会把 Host 改写成上面这个内部域名                      │
└───────────────────────────┬────────────────────────────────────┘
                            │ HTTP → 127.0.0.1:3000
                            ▼
┌────────────────────────────────────────────────────────────────┐
│  dsh-public-bridge.js          ← 本方案核心，必须前台常驻        │
│  监听 0.0.0.0:3000                                              │
│  · HTTP / WebSocket 转发                                        │
│  · Origin / Referer 归一化    ← 解决 /api 403                   │
│  · 302/303 Location 改写                                        │
│  · /mobile-access/* 语义补齐                                    │
│  · /open-in-app/icon/* 图标补齐                                 │
└───────────────────────────┬────────────────────────────────────┘
                            │ HTTP → 127.0.0.1:13080
                            ▼
┌────────────────────────────────────────────────────────────────┐
│  dsh web  （子进程，只绑 loopback）                              │
│  · 鉴权围栏（browser-auth）                                     │
│  · /api browser-trust fence                                     │
└────────────────────────────────────────────────────────────────┘
```

### 三条硬约束（缺一即失败）

1. **dsh 只能绑 `127.0.0.1`** —— 官方明确拒绝绑定 `0.0.0.0`，故必须由外部进程承接公网流量。
2. **桥接必须前台常驻** —— 平台只代理「自启动命令直接子进程」监听的端口，脚本内用 `&`
   fork 出去的后台进程**不被代理**，公网必定 404。
3. **Host 必须原样透传** —— dsh 的会话 Cookie 以 Host（authority）绑定，改写即 401 死循环。

## 四、为什么必须有一层桥接

### 4.1 dsh 拒绝绑定 `0.0.0.0`

```
$ dsh web --host 0.0.0.0
error: --host 0.0.0.0 is intentionally not supported yet for safety:
       it would expose remote code execution to the network;
       use 127.0.0.1 instead
```

这不是配置疏漏，而是**安全设计** —— dsh 具备执行任意代码的能力，直接暴露到网络等同于开放 RCE。
所以必须有一个中间层：内部保持 loopback 隔离，外部由桥接进程承接并做必要的头处理。

### 4.2 平台只代理「直接子进程」

| 启动方式 | 公网可达 |
|---|---|
| `node server.js`（前台运行） | ✅ 通 |
| `bash script.sh`（脚本内 `nohup node server.js &`） | ❌ 404 |

平台在自启动时会做端口探测，但只认**自启动命令的直接子进程**所监听的端口。
后台 fork 出的进程虽然端口在监听，但不被纳入代理范围。

**因此桥接脚本必须前台常驻，dsh 作为它的 `spawn` 子进程。**

## 五、七个坑的根因与修复

### 坑 1：公网别名 404 —— 平台侧路由未绑定

**现象**

```
https://<YOUR-SANDBOX-ID>.app.workbuddy.host/      → 404
https://2100167863587786752.app.workbuddy.host/   → 404
```

返回体只有 19 字节的 `404 page not found`，响应头 `server: CloudStudio Gateway` ——
说明请求根本没到达服务，是网关层直接拒绝的。

**同时刻对照**：内部网关域名返回 `401`（服务健康）。这证明**本机完全正常**，
问题出在平台侧的路由表。

**根因**：平台侧的路由绑定丢失。

**修复**：重新调用发布接口刷新路由绑定：

```bash
RID=$(jq -r .runtimeId /root/.workbuddy-sandbox-publish/state.json)
curl -sS -X POST http://codebuddy.auth-proxy.local/v2/agentos/artifact-releases \
  -H 'content-type: application/json' \
  -d "{\"runtimeId\":${RID},\"artifactType\":\"web\",\"persistent\":true,\"releaseConfig\":{\"port\":3000,\"skipFork\":true,\"appName\":\"<YOUR-SANDBOX-ID>\",\"useAppNameAsDomain\":true,\"expire\":157680000}}"
```

成功返回（实测输出，节选）：

```json
{
  "code": 0, "msg": "OK",
  "data": {
    "releaseId": 1789559675032873242,
    "releaseUrl": "https://<YOUR-SANDBOX-ID>.app.workbuddy.host/",
    "status": "AVAILABLE",
    "releaseConfig": { "port": 3000, "replicas": 1, "expire": 0 },
    "domains": {
      "friendlyDomains": ["<YOUR-SANDBOX-ID>.app.workbuddy.host"],
      "uuidDomains":     ["2100167863587786752.app.workbuddy.host"]
    }
  }
}
```

> **为何请求体要手工拼接**：`runtimeId` 是 19 位大整数（`2100167863587786752`），
> 超过 JavaScript 的 `Number.MAX_SAFE_INTEGER`，用 `JSON.stringify` 会丢精度。
> 因此这里把 `runtimeId` 直接拼进字符串，而不是整体序列化。
> 该接口**首次即返回 `AVAILABLE`**，无需轮询。

> **经验**：判断别名是否打通，看响应体特征 —— 网关 404 是 19 字节纯文本且带
> `server: CloudStudio Gateway`；服务正常时是 dsh 的 68 字节鉴权提示。

### 坑 2：Host 改写导致 401 死循环

**现象**：公网域名下访问，反复 `401`；换成 `127.0.0.1` 访问却正常。

**根因**：dsh 的会话 Cookie **以 Host（authority）绑定**：

```js
function cookieName(authority) {
  return COOKIE_PREFIX + encodeBase64Url(sha256(authority));
}
// 校验时要求：cookie payload 内的 authority === 当前请求的 authority
```

早期版本的桥接为了"让上游看起来是本机请求"，把 Host 强制改写成 `127.0.0.1:13080`。
结果：Cookie 是按公网域名签发的，但校验时用的 authority 变成了 `127.0.0.1:13080`，
**永远对不上** → 反复 401，陷入死循环。

**修复**：**原样透传 Host**，只补 `X-Forwarded-*` 供上游识别真实来源。

```js
function forwardHeaders(req) {
  const headers = { ...req.headers };
  if (!headers.host) headers.host = `${DSH_HOST}:${DSH_PORT}`;
  headers['x-forwarded-host'] = headers.host;
  headers['x-forwarded-proto'] = 'https';
  headers['x-forwarded-for'] = req.socket.remoteAddress || '';
  return headers;
}
```

### 坑 3：`/api` 403 —— browser-trust fence

这是**最隐蔽**的一个 —— 表现为「首页 200、静态资源全部 200，但所有 API 全部 403」。

**现象**

```
/assets/index-BKQ_L1z6.js     200
/assets/vendor-CCJJTK99.js    200
/api/session/list             403   ← 全部 API 403
/api/skills/list              403
...                           403
```

**根因分析（两层）**

dsh 对 `/api` 有一道额外的信任校验：

```js
function isTrustedApiRequest(request, trustedHosts) {
  const hostUrl = parseAuthority(request.headers.host);

  // 第一层：Host 必须在信任列表里
  if (!isLoopbackHostname(hostUrl.hostname) && !isTrustedAuthority(hostUrl, trustedHosts))
    return false;                                    // → 403

  // 第二层：Origin 必须与 Host 同源
  if (header(request.headers, "sec-fetch-site") === "cross-site") return false;
  const origin = header(request.headers, "origin");
  if (origin === undefined) return true;
  return new URL(origin).host === hostUrl.host;      // → 这里也会 403
}
```

**第一层问题**：网关转发时把 Host 改写成内部域名：

```
<PORT>-<SPACE_KEY>.e2b.<REGION>.sandbox.cloudstudio.club
例：3000-<YOUR-SPACE-KEY>.e2b.bj7.sandbox.cloudstudio.club
```

这个域名不在 `--trusted-host` 里。

而 `isTrustedAuthority` 是**精确 hostname 比对，无通配符**，所以无法用 `*.e2b.bj7...`
这种模糊匹配绕过。

**难点**：预热实例阶段 `X_IDE_SPACE_KEY` 指向预热 ID，与网关实际用的值不一致，
**无法静态推导**。

**第二层问题（真凶）**：即使 Host 已加入信任列表，**Origin 仍会卡住校验**：

- 网关把 **Host** 改写成内部域名
- 但浏览器发出的 **Origin** 仍是用户访问的**公网域名**
- 两者 authority 不等 → `new URL(origin).host === hostUrl.host` 返回 `false` → 403

浏览器对 POST 请求**必然**发送 `Origin` 头（这是 fetch 规范的默认行为），
所以这不是边缘情况，而是**必然触发**。

**修复**

1. **Host 学习 + 持久化**：运行时从首个到达的请求上学习真实网关 Host，落盘到
   `.known-hosts.json`，下次启动直接带上，避免反复热重启。

2. **Origin / Referer 归一化**（关键）：转发时把二者重写为与 Host 同一 authority，
   让上游看到的一组头**自洽**。

```js
function forwardHeaders(req) {
  const headers = { ...req.headers };
  if (!headers.host) headers.host = `${DSH_HOST}:${DSH_PORT}`;
  const authority = headers.host;

  // 关键：Origin / Referer 必须归一化到与 Host 同一 authority
  if (headers.origin) headers.origin = `https://${authority}`;
  if (headers.referer) {
    try {
      const ref = new URL(headers.referer);
      headers.referer = `https://${authority}${ref.pathname}${ref.search}`;
    } catch {
      headers.referer = `https://${authority}/`;
    }
  }

  headers['x-forwarded-host'] = authority;
  headers['x-forwarded-proto'] = 'https';
  headers['x-forwarded-for'] = req.socket.remoteAddress || '';
  return headers;
}
```

> **为什么这是合理的**：真实浏览器在公网域名下访问时，`Origin` 与 `Host` **本就应该相等**。
> 它们之所以不等，纯粹是网关改写 Host 造成的副作用。桥接层把它们还原成一致状态，
> 是在**修复网关引入的副作用**，而不是削弱安全校验。

### 坑 4：移动端资源 404 —— 插件网关只监听 loopback

**现象**：`dsh-mobile` 插件的 4 个静态资源全部 404，`console.error` 里有 4 条报错：

```
/mobile-access/extensions/manifest
/mobile-access/custom.css
/mobile-access/custom.js
/mobile-access/extensions/events
```

**排查过程与一个被排除的误判**

第一反应是"插件没启用"。读插件的 `cordis.patch.yml` 后确实看到（节选，省略了若干路径字段）：

```yaml
- id: mobile-access
  name: dsh-mobile
  inject: [webServer, connection]
  config:
    controlFile: !!js dshHomePath('mobile-access/control.json')
    customCssFile: !!js dshHomePath('mobile-access/mobile.css')
    customScriptFile: !!js dshHomePath('mobile-access/mobile.js')
    initiallyEnabled: false        # ← 默认关闭
    listenHost: 127.0.0.1
    listenPort: 3443
    allowedCidrs: [127.0.0.0/8]    # ← 只允许本机回环
    tls:
      mode: disabled
```

于是尝试写入 `control.json`（`{"version":1,"enabled":true}`）让插件启用。
**但实测无效** —— 即使启用，该网关也只绑 loopback 的**随机端口**
（`listenPort` 在运行时模板 `loopbackTemplate()` 里被改写为 `0`：
`listenHost: "127.0.0.1", listenPort: 0, publicAuthorities: ["127.0.0.1"]`），
**永远不会出现在面向公网的主 Web 端口上**。已回退该改动（删除 `control.json`）。

同时确认了插件**装配本身是正常的**：管理 API `/api/mobile-access/*` 已正确挂载到主服务，
返回的是插件自身 JSON 格式的 `{"error":"forbidden"}` 而非 404。

```
$ curl https://<域名>/api/mobile-access/control
{"error":"forbidden"}      ← 插件路由已挂载（403 是插件的信任策略）
```

**根因**：该插件把静态资源挂在**自己的独立网关**上，而那个网关的定位是
服务 loopback 上的**手机 App / 局域网**场景（配合 Tailscale/cpolar/frp 等远程通道），
与公网 Web 前端不是同一条链路。

**客户端其实有降级**

读 `client.js` 发现客户端对 404 有**明确且完整的设计容错**：

```js
if (response.status === 404) {
  legacyScriptRevision = "";
  legacyStyleRevision = "";
  return handleMissingExtensionManifest(clearManifestExtensions, () => ..., signal);
}
```

`handleMissingExtensionManifest` 就是**专为「manifest 不存在」设计的降级分支**。
也就是说这些 404 会优雅降级，**功能不受影响**，只是控制台不干净。

**修复**：在桥接层按插件**自身语义**补齐这 4 个响应，内容直接取自插件源码常量：

| 路径 | 响应 | 来源 |
|---|---|---|
| `/mobile-access/custom.css` | 200 + 注释文本 | `CUSTOM_STYLE_FALLBACK` 常量 |
| `/mobile-access/custom.js` | 200 + 空注册函数 | `CUSTOM_SCRIPT_FALLBACK` 常量 |
| `/mobile-access/extensions/manifest` | 200 + protocol 1 JSON | 插件 manifest 响应结构 |
| `/mobile-access/extensions/events` | 200 + SSE 长连接 | 插件 event stream 格式 |

> **这不是伪造数据**：内容与插件独立网关在「未配置自定义内容」时的响应**完全等价**。
> 补齐只是让控制台干净，不改变任何行为。

### 坑 5：open-in-app 图标 404 —— 无桌面环境提取不到图标

**现象**：这个只在**发消息之后**才出现，比较隐蔽。

```
GET /open-in-app/apps                 → 200  {"apps":["filemanager"]}
GET /open-in-app/icon/filemanager     → 404  {"code":"not-found","message":"no icon for filemanager"}
```

前端从 `/open-in-app/apps` 拿到应用 id 列表后，会去取对应图标，于是产生 404。

**根因**：dsh 的 open-in-app 在 Linux 上按应用探测启动器，并从系统 `.desktop`
文件**提取**真实 PNG 图标（见 `@deepseek-ai/dsh-host-open-in-app` 的 `iconOf` /
`extractAppIcon`）。沙箱是**无桌面环境**：

- `filemanager` 依赖 `xdg-open`，**能**探测到启动器（所以出现在 apps 列表里）
- 但没有对应的桌面图标文件，**图标提取失败**
- 上游于是**主动**返回 404

上游源码注释写得很明确，这是**既定语义**：

> a 404 here means detection didn't find that launcher

**影响评估**：图标在客户端只用于 `<img src>`（`iconUrl()`），是**纯装饰性**资源。
按钮点击走 `POST /open-in-app/open`，与图标无关。**功能零影响。**

**修复**：桥接层为**已确认可用的应用**补一个语义对应的文件夹图标
（`icons/filemanager.png`）。

**刻意不做全局兜底** —— 对未准备图标的 id 仍落到上游，保持其原本的 404 语义：

```
$ curl https://<域名>/open-in-app/icon/unknown-app
404 {"code":"not-found","message":"no icon for unknown-app"}   ← 保持了上游语义
```

### 坑 6：Node 版本 —— 平台版 v22 跑不动 dsh

**现象**：`dsh` CLI 安装成功但**静默失效** —— 无输出、无报错、什么都没有。

**根因**：dsh 入口依赖 Node 的 `import.meta.main` API：

| Node 版本 | `import.meta.main` |
|---|---|
| v22.13.1（平台自带） | `undefined` |
| v24.20.0 | `true` |

在 v22 下该值为 `undefined`，dsh 的主入口判断失败，进程直接静默退出。

**修复**：

1. 用 nvm 升级到 Node v24.20.0
2. 桥接脚本用**绝对路径**拉起 dsh，规避平台运行时版本差异：

```js
const NODE_BIN = '/root/.nvm/versions/node/v24.20.0/bin';
dshProcess = spawn(`${NODE_BIN}/dsh`, dshArgs, {
  cwd: '/workspace',
  env: { ...process.env, PATH: `${NODE_BIN}:${process.env.PATH}` },
});
```

### 附：端口注入冲突

平台自启动注入 `PORT=8089`，但该端口**已被沙箱内置的 `sync_server` 占用**：

```
Error: listen EADDRINUSE: address already in use 0.0.0.0:8089
```

**修复**：桥接脚本**忽略** `process.env.PORT`，固定使用 3000，
与发布时声明的 `--port 3000` 保持一致（网关按端口号路由，两者必须一致）。

```js
const PORT = parseInt(process.env.DSH_PUBLIC_PORT || '3000', 10);
```

### 坑 7：Settings 面板报「加载提供方目录失败」

**现象**：公网域名下打开 `Settings → Models`，面板报：

```
加载提供方目录失败: settings are unavailable in this browser
```

而用 `http://127.0.0.1:3000/` 本地访问同一个页面，**报错完全不出现**。

**排查过程**：

1. 抓取报错文案来源，定位到 `dsh-client-ui-settings-models/lib/client.js:1006`：

```js
if (mirrored.view === void 0) this.failLoad(generation, mirrored.error ?? "settings are unavailable in this browser");
```

2. 用 Playwright 追踪发现：**进入 Models 面板后没有任何网络请求发出**，
   `console` / `pageerror` 均为 0 —— 说明问题不在服务端，客户端根本没发请求。
3. 用 curl 直接验证 `settings.describe`：在公网域名下**返回 200 且数据完整**
   （`writable: true`、`hasDocument: true`、`namespaces` 齐全）。
   即**服务端是放行的，是客户端主动禁用了**。

**根因**：一条确定性的客户端分支链。

```js
// dsh-client-ui-settings/lib/client.js:1345
const persistence = ctx.remote.$host.isLoopback ? "host" : "memory";

// dsh-client-ui-settings/lib/client.js:1237 / 1253 —— memory 直接短路
load()   { if (this.persistence === "memory") return Promise.resolve(); ... }
ensure() { if (this.persistence === "memory") return Promise.resolve(); ... }

// dsh-client-connection/lib/client.js:6344
isLoopback: transport?.ownsHost === true
         || pageLocation === void 0
         || isLoopbackHostname(pageLocation.hostname),

// dsh-client-connection/lib/client.js:6273 —— 只认 localhost / [::1] / 127.x.x.x
function isLoopbackHostname(hostname) {
  if (hostname === "localhost" || hostname === "[::1]") return true;
  const parts = hostname.split(".");
  return parts.length === 4 && parts[0] === "127" && parts.every(p => /^\d{1,3}$/.test(p) && Number(p) <= 255);
}
```

| 环节 | 公网域名 | `127.0.0.1` |
|---|---|---|
| `isLoopbackHostname(location.hostname)` | `false` | `true` |
| `ctx.remote.$host.isLoopback` | `false` | `true` |
| `persistence` | **`"memory"`** | `"host"` |
| `SettingsDescribeMirror` 初态 | **`unavailable`** | `idle` |
| `load()` / `ensure()` | **立即 return，不发请求** | 正常发 `settings/describe` |
| Models 页结果 | **报错** | 正常 |

> **这不是 bug，是 dsh 官方明确的设计。** 见 `dsh-client-ui-settings/README.zh.md:97`：
>
> > 非 loopback 页面没有持久化设置：本 Client 在那里禁用 Host 持久化，
> > 因此 scope 以 `unavailable` 起步且从不跨线路；尽管 Connection 认证覆盖 API，
> > 它支撑的每一行仍在那里无效。

**修复方案**：利用官方 index 注入管线，投放页面全局 `__DSH_TRANSPORT__`。

`isLoopback` 的第一个分支读 `globalThis.__DSH_TRANSPORT__`
（`dsh-client-connection/lib/client.js:6307`），该对象在官方类型 `ClientTransportHooks`
中的 `ownsHost` 语义是「本页面完全拥有 Host，没有第三方能触达它」。
把它设为 `true` 即可让 `isLoopback` 报告 `true`。

关键点是**用官方的注入机制而非改写前端产物**：`@deepseek-ai/dsh-host-webserver`
暴露 `webserver/index-inject` 事件收集注入行，其中 `kind: 'global'` 行的渲染结果正是
`<script>globalThis["__DSH_TRANSPORT__"] = {"ownsHost":true}</script>`。
**这正是 `@deepseek-ai/dsh-client-connection` 自己投放 `__DSH_CONNECTION_RECOVERY__`
所用的同一机制**：

```js
// dsh-client-connection/lib/index.js:760 —— 官方自己的用法
webCtx.on("webserver/index-inject", (table) => {
  table.push({ kind: "global", name: "__DSH_CONNECTION_RECOVERY__", value: recovery });
});
```

修复插件（`dsh-local-loopback-trust`）的做法与之完全对称：

```js
ctx.inject(['webServer'], (webCtx) => {
  webCtx.on('webserver/index-inject', (table) => {
    table.push({ kind: 'global', name: '__DSH_TRANSPORT__', value: { ownsHost: true } });
  });
});
```

**时序由 dsh 自身担保**：该行被插在 `<head>` 开头、先于前端 module bundle 执行；
紧随其后的 `__DSH_BOOT_READY__` 尾脚本保证客户端入口会等待注入表就绪。

**不改变任何网络行为**：`createWebConnectionRpc(transport?.fetch, transport?.openStream)`
只消费 `fetch` / `openStream` 两个可选字段，只写 `ownsHost` 时二者保持 `undefined`，
RPC 回落到 `globalThis.fetch` 与既有 WebSocket 路径。

**注册方式**（插件包需声明 `dsh.bundle` 才能作为 profile 层加载）：

```json
// /root/.dsh/profiles/web/node_modules/dsh-local-loopback-trust/package.json
{ "dsh": { "bundle": { "patch": "./cordis.patch.yml" } } }
```

```json
// /root/.dsh/profiles/web/package.json
{
  "dependencies": { "dsh-local-loopback-trust": "file:./node_modules/dsh-local-loopback-trust" },
  "dsh": { "profile": { "bundles": ["...", "dsh-mobile", "dsh-local-loopback-trust"] } }
}
```

> ⚠️ **踩坑记录**：漏写 `dsh.bundle` 会导致 dsh **启动即崩**，报错非常明确：
> `profile bundle "dsh-local-loopback-trust" declares no dsh.bundle in its package.json`。
> 另注意：排查时若看到反复报错的日志，先确认是不是**旧进程残留**在刷日志
> （旧进程会持续输出同一段堆栈，造成"改了没生效"的错觉）。

**安全边界（务必阅读）**：

`ownsHost: true` 的原始语义是「Host 只被本页面触达」。反向代理 / 公网暴露场景下
该前提**并不成立** —— 任何持有访问凭据的人都能连上这个页面。开启后，settings 文档
（含凭据字段）对所有能访问该 URL 的人**可读写**，影响范围包括：

- Settings → General：默认模型、默认工作区等（`SettingsDocumentStore`）
- Settings → Models：提供方配置与 API Key 等凭据字段
- 其他一切以 `remote.$host.isLoopback` 为守门的客户端插件

这确实是**绕过一道有意的安全边界**。因此插件**默认关闭**，只在显式配置
`enabled: true`（或环境变量 `DSH_TRUST_PROXY_PAGE=1`）时才注入。

**关闭方式**：把 `enabled` 改为 `false`，或从 `cordis.patch.yml` 移除该 insert 条目。
改动后 dsh 会热重载该 profile 层（`patchReload: live`）；未生效则重启 dsh 进程。

**验证方法**（`restart.sh` 已内置自检）：

```bash
# 直接看 index.html 是否被注入
TOKEN=$(grep -oE 'token=[A-Za-z0-9_-]+' /workspace/dsh-公网访问地址.txt | head -1 | cut -d= -f2)
curl -s "http://127.0.0.1:13080/?token=$TOKEN" -c /tmp/ck -o /dev/null
curl -s -b /tmp/ck http://127.0.0.1:13080/ | grep -o '__DSH_TRANSPORT__[^<]*'
# 期望输出：__DSH_TRANSPORT__"] = {"ownsHost":true}
```

## 七、验收方法

**核心原则：穷尽式核对，而非抽样。** 抽样容易漏掉「只在特定交互后才触发」的请求
（如坑 5 的图标 404，只有发消息后才出现）。

### 7.1 鉴权闭环

```bash
H=<YOUR-SANDBOX-ID>.app.workbuddy.host

# ① 无凭据 → 401（鉴权围栏生效）
curl -s -o /dev/null -w "%{http_code}\n" "https://$H/"

# ② 带 token → 303 + Set-Cookie
curl -s -i "https://$H/?token=<TOKEN>" | grep -iE '^(HTTP|location|set-cookie)'

# ③ 携带 Cookie → 200
CK=$(curl -s -i "https://$H/?token=<TOKEN>" | grep -i '^set-cookie' | sed 's/^[Ss]et-[Cc]ookie: //' | cut -d';' -f1)
curl -s -o /dev/null -w "%{http_code}\n" -H "Cookie: $CK" "https://$H/"
```

### 7.2 浏览器端全量验证

用 Playwright 驱动真实 Chromium，**拦截所有请求**并核对状态码，
同时模拟完整交互流程（关闭公告 → 新建会话 → 输入 → 提交 → 切模型 → 开设置）。

验证清单：

- [ ] 主文档 200，标题正确
- [ ] 所有静态资源 200（含 MB 级 vendor bundle）
- [ ] 所有 `/api/*` 200
- [ ] `/mobile-access/*` 4 项 200
- [ ] `/open-in-app/icon/filemanager` 200
- [ ] `/plugins/??...`（多个插件 bundle 合并请求）200
- [ ] WebSocket 已连接且未断开
- [ ] `pageerror` 计数为 0
- [ ] `console.error` 计数为 0
- [ ] 无失败请求（`requestfailed`）
- [ ] 无 4xx/5xx 响应
- [ ] **Settings → Models 面板无报错，且 `settings/describe` 返回 200**（坑 7 专项）
- [ ] **`llm/listProviders` 与 `llm/listConfigurableProviders` 返回 200**
- [ ] **`globalThis.__DSH_TRANSPORT__` 已注入且为 `{ ownsHost: true }`**

> ⚠️ **一条重要经验**：只看"请求是否 4xx/5xx"是**不够的**。
> 坑 7 的表现恰恰是 **`settings/describe` 这个请求压根没被发出** ——
> 所有已发生的请求都是 200，但功能依然不可用。
> 因此验证时必须同时确认**该发的请求确实发了**，而不只是检查已发请求的状态码。
> 这也是为什么 7.3 里强调"必须模拟真实交互"。

### 7.3 常见误判提醒

| 误判 | 正确理解 |
|---|---|
| 看到 401 就以为服务坏了 | **401 是健康信号** —— 说明请求到达了 dsh 的鉴权层。网关 404 才是路由问题（19 字节纯文本 + `server: CloudStudio Gateway`） |
| 静态资源 200 就以为全好了 | **必须单独验证 `/api`** —— 二者走不同的校验路径 |
| 首页能开就以为功能正常 | **必须模拟真实交互** —— 部分请求只在交互后触发 |
| 所有请求都 200 就以为全绿 | **还要确认关键请求确实发生了** —— 客户端短路会导致请求根本不发出（见坑 7） |
| 点击元素超时就是页面坏了 | 可能是**首启公告/API Key 引导遮罩**挡住，属正常产品行为，需先点 `Configure later` 或关闭 `role="dialog"` |
| 改了配置重启后报错没变 | 可能是**旧进程残留**在持续刷日志，先确认没有历史进程存活 |
| `GET /api/xxx` 返回 404 就是接口不存在 | **`/api` 是 RPC over POST**，GET 必然 404，跟接口是否存在无关（见 §7.4） |
| RPC 返回 HTTP 200 就是成功了 | **业务校验失败时状态码仍是 200**，错误藏在 `result.ok === false`（见 §7.4） |
| `/session/<id>` 直链 404 就是路由有 bug | dsh 前端**无 URL 路由**，上游 dsh 直连同样 404，属既有设计 |
| 新建会话后总数没变就是创建失败 | dsh 对空会话 **lazy 复用**，发消息后才落库并自动生成标题 |

### 7.4 `/api` RPC 协议（排障必读）

dsh 的 `/api/*` **不是 REST，而是 RPC over POST**。写探针或做二次开发前必须了解，
否则会产出一堆假红灯。真实信封格式（从页面请求捕获）：

```json
POST /api/session/list
Content-Type: application/json

{
  "type": "client-request",
  "rpcId": "<uuid>",
  "method": "session/list",
  "payload": { "args": { "_request": {} } }
}
```

外层 `payload` 是必需的；内层 `args` 的**形状逐端点不同**：

| 端点 | `args` 形状 |
|---|---|
| `session/list` | `{"_request": {}}` |
| `settings/describe` | `{}` |
| `llm/listProviders` | `{}` |
| `llm/listConfigurableProviders` | `{}` |
| `session/modelCatalog` | `{}` |
| `agentPresets/list` | `{}` |
| `dynamicCordisRunner/inventory` | `{}` |
| `credentials/describe` | `{"refs": ["DEEPSEEK_API_KEY"]}` |
| `subagents/list` | `{"parentSessionId": "<sessionId>"}` |
| `commands/list` | `{"agentId": "<sessionId>"}` |
| `skills/list` | `{"request": {"sessionId": "<sessionId>"}}` |

**三类典型错误与对应报错**：

| 写法 | 报错 |
|---|---|
| `GET` 而非 `POST` | HTTP **404** `not found` |
| 缺 `payload` 层 | `invalid client-request message` + `payload` expected nonoptional |
| `args` 形状不对 | `typert gateway: <endpoint>: args fields do not match the descriptor: missing "<字段>"` |

> ⚠️ **以上三种情况 HTTP 状态码都是 200**。判断成功必须看
> `result.ok !== false`，而不能只看 HTTP 码。

**`session/list` 返回结构**：

```json
{"result": {"ok": true, "value": {"items": [ {...} ]}}}
```

会话标题位于 `item.projections.values.title`，`null` 表示空会话（尚未发消息）。
其余统计在 `item.projections.values.sessionStats`（`turns` / `steps` 等）。

**一段可直接用的探针模板**（浏览器控制台或 Playwright `evaluate`）：

```js
async function rpc(method, args) {
  const r = await fetch('/api/' + method, {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    credentials: 'include',
    body: JSON.stringify({
      type: 'client-request',
      rpcId: crypto.randomUUID(),
      method,
      payload: { args },
    }),
  });
  const j = await r.json();
  const res = j.result || {};
  return { http: r.status, ok: res.ok !== false, value: res.value, error: res.error };
}

// 用法
await rpc('settings/describe', {});                       // 坑 7 专项检查
await rpc('credentials/describe', { refs: ['DEEPSEEK_API_KEY'] });
await rpc('session/list', { _request: {} });              // 会话列表
```

## 十、移动端排版优化插件（可回滚）

### 10.1 为什么需要它

dsh 官方 Web 界面按**桌面宽屏**设计，在 390×844 手机视口下有几处明显不适配：

| 问题 | 原生实测值 |
|---|---|
| 消息列上下间距过大 | `_column` 的 `row-gap: 10px` 与各 `flowItem` margin **双重叠加** |
| 用户消息时间戳独占一行 | `timeStart` 的 `flex: 1 1 100%`（**主动撑满整行**），占 342×20px |
| 模型回复无身份标识 | 裸 `<p>`，与用户消息视觉上难以区分 |
| 气泡偏肥 | `padding: 10px 16px` / `border-radius: 22px` |
| 操作按钮偏小 | 28×28px，触屏上不好点 |

### 10.2 插件实现

`/workspace/dsh-公网部署/plugin-dsh-mobile-polish/`：

```
plugin-dsh-mobile-polish/
├── README.md               # 完整说明（含回滚、验证、限制）
├── package.json            # 声明 dsh.bundle.patch
├── cordis.patch.yml        # enabled / maxWidth / verbose 配置
└── lib/
    ├── index.mjs           # 插件主体，~140 行
    └── mobile-polish.css   # 样式，~200 行
```

原理是挂 dsh 官方暴露的注入点，**只注入 CSS，不注入任何 JS**：

```js
ctx.inject(['webServer'], (webCtx) => {
  webCtx.on('webserver/index-inject', (table) => {
    table.push({ kind: 'style', text: css });   // → <style> 插入 <head>
  });
});
```

`webserver/index-inject` 支持 `global` / `script` / `script-src` /
`script-preload` / `style` / `html` 六种 `kind`，本插件只用 `style`。
因为不注入 JS，所以没有运行时副作用，关掉后刷新页面即恢复原样。

### 10.3 类名选择器：必须用子串匹配

dsh 前端用 CSS Modules，类名形如 `Sixlwa_bubble`、`EvIC1a_column`、
`xzv4MW_timeStart` —— **hash 前缀每次构建都会变**，所以只能用：

```css
[class*="_bubble"] { ... }   /* ✅ 稳定 */
.Sixlwa_bubble { ... }       /* ❌ 下次构建即失效 */
```

代价是选择器优先级低，因此所有规则都带 `!important`。

### 10.4 实测效果

同一会话同一内容，真机复刻视口 **381×741 / DPR 2.8375 / Android Chrome UA**，
插件 OFF / ON 逐项 computed 比对：

| 指标 | OFF | ON | 判定 |
|---|---|---|---|
| `_column` row-gap | `10px` | **`0px`** | ✅ |
| `--dsh-chat-flow-gap` | `16px` | **`6px`** | ✅ |
| 时间戳 flex | `1 1 100%` | **`0 0 auto`** | ✅ |
| 时间戳宽度 | 309px | **28px** | ✅ |
| `actions` 高度 | 74px | **34px** | ✅ |
| `userRow` 高度 | 134px | **94px** | ✅ |
| 代码块被切断 | `list[in`+`t]` | **完整 + 横向滚动** | ✅ |
| `composerSeat` 高度 | 141px | **125px** | ✅ v8 |
| 底部统计文字 | 93/116 截断 | **116/116 完整** | ✅ v8 |
| 点会话后侧栏 | 335px 不收回 | **20px 自动收回** | ✅ v8 |
| JS 异常 | 0 | **0** | ✅ |

其中**时间戳那一条是最关键的修复**：原生 `flex-basis` 为 `100%` 且
`flex-grow` 非 0，元素会被强制拉满整行 —— 只写 `width: auto` 完全无效，
必须覆盖 `flex` 简写本身。

> **一个真实的误判教训**：排查过程中曾一度认为插件「完全没生效」，
> 因为测量到的 `flex` 仍是 `1 1 100%`、gap 仍是 `10px`。后来发现是
> **测量时页面处于移动端侧栏布局（`_column` 宽度仅 260px）**，
> 而非聊天主体区域，DOM 状态不同。改用 `getComputedStyle` 逐项比对后
> 才确认真实生效情况。**排查 CSS 问题一定要先确认测量的是同一个 DOM 状态。**

> **另一个教训**：早期测试用 390×844 / DPR 2，与用户真机 381×741 /
> DPR 2.8375 不一致，导致漏测了一批问题。**测试视口必须复刻真机**，
> 否则测出来的"通过"是假的。

#### 10.4.1 v8 修复的三个真机问题

用户真机实测反馈 5 个问题，其中 3 个由本插件修复（另 2 个属沙箱环境限制，见 10.6）：

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | 底部输入区太空旷 | `dsh-mobile` 用 `[data-dsh-mobile-center] [class*="_composer"]` 把 padding 锁在 8px，我的 (0,1,0) 压不过 (0,2,0)；提到 (0,2,0) 后又输给「非 `@media` 规则在平手时胜」 | 优先级抬到 **(0,3,0)**（加 `[class]`），141px → **125px** |
| 2 | 底部统计文字被截断 | 不是 `text-overflow` 的问题，而是 label `flex: 0 1 auto` **被压缩** | 改 `flex: 0 0 auto`，93/116 → **116/116** |
| 5 | 点会话后抽屉不收回 | dsh-mobile 的 handler 挂在 `.dshm-drawer` 上，但**该元素从未渲染**（实测 `length === 0`），handler 等于没绑 | 注入 JS 监听会话行点击 → 调用原生 `backdrop.click()`，335px → **20px** |

**问题 #5 的完整排查链**值得记录，因为它不是「功能坏了」而是「代码没跑」：

```
1. 确认复现   → 会话切换成功(selected 变了) 但宽度 335 不变
2. 找到意图   → dsh-mobile/mobile-layout.js:357 有 closeDrawerAfterSessionAction
3. 为什么没跑 → document.querySelectorAll('.dshm-drawer').length === 0
                handler 绑在不存在的元素上
4. 确认通路好 → 点 .dsh-native-mobile-backdrop 右缘 → 335 → 20 ✅
5. 结论       → 不是关闭坏了，是"点会话行"这条捷径没人接
6. 解法       → 复用原生遮罩的 click()，而不是自己改 React 状态
```

> **教训**：遇到「交互没反应」，先确认**代码有没有执行**，再去怀疑逻辑。
> 本例中 handler 的判定条件（`role="treeitem"` + `aria-selected`）其实
> **完全正确**，DOM 也确实带这些属性 —— 如果只盯着条件看，会永远找不到原因。

#### 10.4.2 v9 字号 / 行高 / 顶栏三项调整

用户要求：**字号改 12px、行高减 2px、顶部压缩**。

| 项目 | v8 | v9 | 说明 |
|---|---|---|---|
| 正文字号 | 14px | **12px** | `--dsh-content-font-size` |
| 正文行高 | 24px | **22px** | −2px |
| 气泡行高 | 21px | **19px** | −2px |
| 输入框行高 | 24px | **22px** | −2px |
| `header` | 76px（占视口 10%） | **56px** | 回收 20px |
| `titleRow` | 32px | **26px** | |
| `tabs` | 28px | **24px** | |
| **内容可视区** | 665px | **685px** | **+20px** |

**坑 1：变量定义在 `body`，不是 `:root`**

```js
document.documentElement.getPropertyValue('--dsh-content-font-size')  // → ""（空）
document.body.getPropertyValue('--dsh-content-font-size')             // → "14px"
```

只在 `:root` 设变量**无效** —— `body` 自己有定义会盖过继承值。必须
`:root, body { ... }` 同时覆盖。另外行高 `24px` 是**硬编码**不走变量，
必须单独用选择器改。

**坑 2：顶栏又是 `dsh-mobile` 的 `[data-dsh-mobile-header]` 前缀**

第一版只写 `[class*="wSkVaW_titleRow"]`（(0,1,0)），顶栏只从 76 掉到 65px。
CDP 查出对手：

```css
[data-dsh-mobile-header] [class*="_titleRow"] { min-height: 32px !important; }  /* (0,2,0) */
[data-dsh-mobile-header] [class*="_tabs"]     { min-height: 28px !important; }  /* (0,2,0) */
```

加同前缀 + `[class]` 抬到 **(0,3,0)** 才彻底压过。

> **这是第三次踩同一个坑**（v7 的 `-center`、v8 的 `-center`、v9 的 `-header`）。
> **规律**：只要 `dsh-mobile` 也管这块，它必用 `[data-dsh-mobile-*]` 属性前缀把
> 优先级抬到 (0,2,0)。**看到「我写了规则但不生效」，先去 CSSOM / CDP 搜
> `[data-dsh-mobile-` 开头的选择器。**

**坑 3：自己撞自己**

气泡行高实测 18px 而非设的 19px —— 因为本插件**自己的**另一处规则写了
`[class*="_bubble"] { line-height: 1.5 }`（12 × 1.5 = 18px）。已删除该条。

> **教训**：改样式前先 `grep` 自己文件里有没有同族规则，别只盯着外部竞争者。

> **关于 12px 的可用性提示**：12px 在手机上偏小（iOS/Android 正文舒适区间
> 多为 14~16px）。若长时间阅读觉得吃力，把 `--dsh-content-font-size` 调回
> `13px`（行高相应改 `23px`）即可，改一处全局生效。

#### 10.4.3 v10 块间距压缩 —— 找到「行间距大」的真正元凶

用户反馈：

> 这个行间距怎么这么大？？？？？？现在行间距是多少

**排查结论：行高不是主因，块间距才是。**

实测行高确实是 22px（比值 1.83，偏松），但真正的视觉空洞来自
**markdown 段落 margin = 16px**：

```
段落本身高 22px，前后各留 16px → 间隙占行高 73%
11 处兄弟间隙全部 16px：
  p/当前系统状态摘要 → p/运行时长        16px
  p/运行时长         → ul/已运行约 2 小时  16px
  ul/已运行约 2 小时  → p/磁盘           16px
  ...（共 11 处）
```

**根因：v4 起一直在压 `--dsh-chat-flow-gap`（消息与消息之间），
从未碰过消息内部 markdown 段落的 margin。** 这两者是不同层级，
只压外层 gap，内层照样空旷。

调整内容：

| 位置 | v9 | v10 | 说明 |
|---|---|---|---|
| **段落块间距** | **16px** | **6px** | ← 本次核心 |
| 标题上/下间距 | 16px | 10px / 4px | 保留分段感 |
| 正文行高 | 22px | **18px** | 比值 1.83 → 1.50 |
| 气泡行高 | 19px | **16px** | |
| 输入框行高 | 22px | **18px** | |
| 代码块行高 | 19px | **17px** | |
| 消息间距 | 6px | **4px** | |

**实测收益**（同一段真实内容：12 个块 / 17 行）：

| | 计算 | 合计 |
|---|---|---|
| 推算 v9 | 17 行 × 22px + 11 处 × 16px | **550px** |
| 实测 v10 | 17 行 × 18px + 块间距 | **321px** |
| **节省** | | **229px（41.6%）** |

**坑 1：必须同时改 `margin-top` 和 `margin-bottom`**

原生用长手写法 `margin-top: 16px; margin-bottom: 16px`，相邻块触发
**margin collapse（外边距折叠）**，结果取 `max(16,16) = 16px`，**不是 32px**。
若只改 `margin-top: 6px` 而留 `margin-bottom: 16px`，折叠后仍是 **16px** —— 白改。
必须两条同时改。

**坑 2：同一个属性在文件里只能声明一次（第三次"自己打自己"）**

v10 第一版改完，块间距 11 处全部 6px ✅，但 `hWmORq_body` 行高死活停在 22px ❌：

```css
/* 文件开头（v10 新增） */
[class*="hWmORq_body"] { line-height: 18px !important; }
/* 文件第 532 行（v9 遗留） */
[class*="hWmORq_body"] { line-height: 22px !important; }   /* ← 后写者胜 */
```

两条选择器**完全相同**、优先级同为 (0,1,0)、都在 `@media` 内 → **后写者胜**，
开头那条白写。这是本插件第三次同类问题（v9 `_bubble` 的 `1.5`、v9 `hWmORq`
的 22px、v10 再次复发）。

> **定性结论：同一属性全文件只能有一处声明。** 跨版本迭代时尤其危险 ——
> 新规则加在文件开头，老规则还躺在文件中间，两边都以为自己在管。
> 改完行高/字号，务必 `grep -n "line-height" mobile-polish.css` 自查一遍。

**关于「块间 vs 块内」的通用教训**：


**坑 1：压过头 —— 按钮跑到左侧浮空**

v11 中间版本给操作按钮加夹逼想把 34px 压到 28px：

根因：这排依赖两组必须配对的属性（都在第 6 节）：

```css
/* 父容器：负责"靠右" */
[class*="xzv4MW_actions"] { justify-content: flex-end !important; flex-wrap: nowrap !important; }
/* 按钮：负责"不伸缩" */

```

v11 插入的 `flex: 0 0 28px` 让 `flex-basis` 覆盖 `width`，
父容器的 `flex-end` 因基准变化算错偏移 → 按钮组整体左移。

**修法：整体回滚按钮尺寸改动**，v11 段只留容器高度归零，不碰任何尺寸/对齐属性。

> **教训：压缩布局时，「改尺寸」和「改对齐」是两件事。**
> 只压尺寸通常安全；一旦动了 flex 基准（`flex` / `flex-basis` /
> `justify-content`），就可能打破原生对齐契约。
>
> **判据：改完必须看截图，不能只看数字。**
> 这次数字全对（28×28 ✅）但视觉是坏的 —— 只信 `getBoundingClientRect` 会漏掉。

**坑 2：探测脚本拿到屏幕外元素，给出假阳性**

排查中两个脚本结论矛盾：一个报按钮 x=**16**（左侧），一个报 x=**321**（右侧）。

> **教训：DOM 查询必须限定「视口内可见」**，否则会拿到假阳性。
> 之前测「底部文字截断」时也踩过同类问题。

#### 10.4.5 v12 零高占位块的白吃间隙 —— 「工具调用」与「正文」之间那块空洞

用户又发来真机截图，圈了两处：

1. **「工具调用」块与「回复正文」之间空了一大块**（视觉约 40~50px）
2. **时间戳 `01:49` 单独占一行**

同时问：「我能用 32g？容器内存应该没有这么大吧」。

**第一步：审计脚本又漏了**

沿用 v11 的审计脚本（按纵向占位排序），结果里**根本没有异常项** —— 所有显式间距
都已压到 2~3px。于是写 `diag-gap.py` 直接量相邻块的**真实间隙**（rect 相减）。

第一条线索：14 个 `flowItem` 的前间隙 **10px ~ 18px 不等**，
而 CSS 里 `--dsh-chat-flow-gap` 明明设成了 `2px`。

**第二步：找「谁在吃间距」—— 零高块现身**

写 `probe-zeroh.py` 把消息列子元素**逐个打印**（不按高度筛），看到：

```
flowItem  h=0   cls=EvIC1a_spacer  margin-top=0  margin-bottom=0
flowItem  h=0   cls=EvIC1a_spacer  margin-top=0  margin-bottom=0
flowItem  h=0   cls=EvIC1a_spacer  margin-top=0  margin-bottom=0
```

**它们的 margin 全是 0** —— 说明我最初的判断（「零高块白吃 margin」）是错的。

前两轮之所以都漏掉它们，是因为审计脚本有 `if (height > 30)`
—— **零高节点被整体过滤，从未进入视野。**

再查父容器：

```js
getComputedStyle(column)  // { display:"flex", flexDirection:"column", gap:"10px" }
```

**第三步：真凶 = flex `gap`，它对零高子项照样生效**

`gap` 在 flex 布局里**按子项数量**分配空隙，**与子项高度无关**。
3 个零高块夹出 4 道间隙 → 4 × 10px = **40px 纯浪费**。

> **反直觉点**：`height: 0` 的 flex item **不是隐形的**。
> 只要它是 flex item 就照样触发一道 `gap`。
> 想靠「给零高块设 margin: 0」省空间 —— 无效，gap 与 margin 不是同一机制。

**第四步：又是 `dsh-mobile` 属性前缀坑（第 5 次）**

第一版 `[class*="EvIC1a_column"] { gap: 4px !important; }` **没生效**。
CDP 查匹配规则：

```
[data-dsh-mobile-message-column] { gap: 10px }     ← 胜出
[class*="EvIC1a_column"]         { gap: 4px !important }
```

两条同为 (0,1,0)，我后写却输了 —— `dsh-mobile` 插在更靠后的样式表位置。
（第 5 次栽同一坑：v7 / v8 / v9 / v11 / v12）

修法：加同前缀 + `[class]` 抬到 (0,2,0)：

```css
/* 【v12-1】零高占位块：真凶是 flex gap，不是 margin */
[data-dsh-mobile-message-column] [class*="EvIC1a_column"][class],
[data-dsh-mobile-message-column] [class*="_column"][class],
[class*="EvIC1a_column"][class],
[class*="_column"][class] {
  gap: 4px !important;
}
```

复测：`{"gap":"4px","rowGap":"4px","display":"flex"}`，
14 个 flowItem 前间隙**统一 4px** ✅

**第五步：零高块自身 margin 显式归零兜底**

```css
[class*="EvIC1a_column"] > [class*="EvIC1a_flowItem"],
[class*="_column"] > [class*="_flowItem"] {
  margin-top: 0 !important; margin-bottom: 0 !important;
}
[class*="_flowItem"][data-turn-process-answer],
[class*="_flowItem"]:has([class*="hWmORq_root"]) { margin-top: 0 !important; }
```

**第六步：时间戳那行 —— 它是「操作栏」的搭便车乘客**

「`01:49` 为什么单独占一行」的答案在 DOM 结构里：

```

  ├── xzv4MW_timeStart   28 × 11px   ← 时间戳（搭便车）
```

**这一行的高度由 34px 的操作按钮决定，不是时间戳撑的。**
把它拆成独立小行反而更省（11px < 36px），但属结构性改动、收益不稳，
本次只去 `margin-top`：

```css
[class*="TS9iAW_root"], [class*="xzv4MW_root"] {
  margin-top: 0 !important; padding-top: 0 !important; padding-bottom: 0 !important;

[class*="xzv4MW_timeStart"], [class*="xzv4MW_timeEnd"] {
```

> 关于 `32g`：那是**宿主机总内存**（dsh 状态栏读 `/proc/meminfo`），
> 容器 cgroup 限额远小于此。属显示口径问题，不是布局问题。

#### 10.4.6 v13-B 时间戳不再独占一行 —— 一次「只看容器高、没看内部行数」的误判

用户追问：**「那你这时间还是另外占用了一行啊」**

v12 的解释是「那行 36px 高由 34px 按钮决定，时间戳只是搭便车」——
**这个解释不完整，漏掉了最关键的一点：容器内部折成了 3 行。**

**真因**（量容器内部每个子项的 y 坐标）：

```
xzv4MW_actions   w=327px   flex-wrap:wrap   justify-content:flex-end
  ├─ 按钮 ×6    34×34   y=576   ← 第 1 行
  ├─ Q51KRG     34×34   y=576   ← 第 1 行
  └─ timeEnd    28×11   y=588   ← 第 3 行   ★ 被折行挤下来的
实际行数 = 3
```

6 个 34px 按钮（204px）+ 间距（30px）+ 时间戳（28px）超过 327px，
`flex-wrap: wrap` 把时间戳挤到了独立一行。

> **教训：判断"某元素占多少空间"，不能只看它的 `height`，
> 必须看它内部子项的 y 坐标分布（即真实行数）。**
> v12 就是栽在「容器 36px → 按钮 34px → 得出结论」这条推理链上。

**方案 B（用户选定）**：只让时间戳归位，不碰按钮尺寸。

```css
[class*="xzv4MW_actions"], [class*="TS9iAW_actions"] { flex-wrap: nowrap !important; }
[class*="TS9iAW_root"], [class*="xzv4MW_root"] { gap: 0 !important; }
[class*="timeStart"], [class*="timeEnd"] {
  order: -1 !important; margin-right: auto !important;
  flex: 0 0 auto !important; align-self: center !important;
}
```

| 指标 | 改前 | 改后 |
|---|---|---|
| 内部**实际行数** | **3 行** | **1 行** ✅ |
| 时间戳位置 | x=315（独立行） | **x=16（最左）** ✅ |
| 时间戳 `order` | `0` | **`-1`** ✅ |
| 时间戳 `margin-right` | `0px` | **`59.47px`** ✅ |
| 按钮尺寸 | 34×34 | **34×34（未变）** ✅ |
| 按钮最右 | 309 | **343（仍靠右）** ✅ |

**为什么这次没像 v11 那样把按钮搞浮空：**

| | v11（失败） | v13-B（成功） |
|---|---|---|
| 改了什么 | 按钮加 `flex: 0 0 28px` | 容器加 `nowrap` + 时间戳 `order/margin` |
| 判据 | **动了子项的 `flex` 基准** ❌ | **只动容器换行策略 + 子项排序** ✅ |

> **结论：动子项的 `flex`/`flex-basis` 会破坏与父容器 `justify-content` 的配对；
> 动容器的 `flex-wrap` + 子项的 `order` 则安全。**

回滚验证 **6/6 通过**（操作栏高 36→54px、时间戳 order −1→2、
时间戳宽 28→351px、按钮 34→28×28、列 gap 4→10px，全部回落原生值）。

#### 10.4.7 v14 markdown 正文排版优化 —— 一次 `display: inline` 反而更差的教训

用户反馈：**「md 回复正文格式能不能优化，这个格式好丑」**

造了一篇含全要素的 markdown 回复，实测出 6 处问题：

| 元素 | 改前实测 | 问题 |
|---|---|---|
| H3 标题 | lh20，mt6 mb2 | 与正文仅隔 2px → **像加粗正文，无层级感** |
| **行内 code** | **`display:inline-flex`，h=23px** | **比正文行高 18px 还高 → 撑高整行、句号成孤字** |
| 代码块容器 | 128px，其中 header 占 **46px** | header 空档过大 |
| 代码块 pre | lh **19.375px** | 非整数行高，渲染发虚 |
| blockquote | pl 14px | 比列表缩进小，不统一 |
| 表格行 | h **39px** | 行高过大，表格很空 |

**核心修复：行内代码 —— A/B/C 三方案隔离实测**

| 方案 | 代码高 | 代码宽 | 判定 |
|---|---|---|---|
| 改前 `inline-flex` | 23px | 81px | ← 撑高整行 |
| A: `display: inline` | **34px** | **296px** | ❌ **更差！** |
| **B: `inline-block` + `vertical-align: middle`** | **17px** | **83px** | ✅ **最优** |
| C: `inline` + `padding: 0` | 32px | 296px | ❌ 更差 |

> **为什么 A/C 反而更差**：`display: inline` 会让元素变成匿名行内盒，
> **盒子塌陷后宽度变成整行 296px（撑满）**，高度算成内容盒 34px。
> **只有 `display: inline-block` 能同时约束宽高。**
>
> **教训：`inline` 和 `inline-block` 在 flex 语境下行为完全不同，别想当然。**
> 第一版就是直接写 `display: inline`，结果比原生还难看 ——
> 若不是做了三方案对比，就会把「优化」做成「劣化」。

**结果**

| 指标 | 改前 | 改后 |
|---|---|---|
| 行内代码高 / 行高 | 23px / 19px | **17px / 13px** |
| 代码块 pre 行高 | 19.375px | **18px**（锐利） |
| **表格高** | **117px** | **75px**（−42px） |
| 表格行高 | 39px | **25px** |
| H3 间距 | 6/2px | **11/5px**（**刻意加回**） |
| md 总高 | 670px | 680px |

> **关于标题间距**：这是唯一一处主动加大的改动。v11 曾把标题压到 mb2，
> 结果标题与下文糊在一起。**该省的是段落之间的冗余，不是标题的呼吸空间** ——
> md 总高略增 10px 是有意的取舍。

回归 **7/7 全绿**，回滚验证 **7/7 通过**（表格高 75→129px、
行内代码 17→21px、H3 间距 11/5→32/16px、md 总高 680→1054px）。

### 10.5 部署与回滚

```bash
cd /workspace/dsh-公网部署

./polish.sh on       # 启用（自动备份 profile → 同步文件 → 注册 bundle → 重启）
./polish.sh off      # 关闭（只改 enabled: false，文件全保留）
./polish.sh revert   # 彻底回滚（恢复 profile + 删插件目录 + 重启）
./polish.sh status   # 查看状态
./polish.sh backup   # 手动备份
```

三层回滚保障：

| 层级 | 手段 | 命令 |
|---|---|---|
| 1. 开关级 | 只改 `enabled: false`，文件全保留 | `./polish.sh off` |
| 2. 配置级 | 从 `package.json.polish-backup-*` 恢复 | `./polish.sh revert` |
| 3. 源码级 | 插件源码独立在 `plugin-dsh-mobile-polish/`，profile 副本删了也不丢 | 手工 `cp` |

**`revert` 的修复过程（重要踩坑）**：初版 `revert` 会**先删插件目录、
后恢复 profile**，且备份时机有误（`on` 时先备份再注册，导致备份出的
就是一份「已含本插件」的配置）。两者叠加的结果是：`revert` 报告成功，
但 profile 里仍残留 bundle 引用、而目录已被删除 —— **dsh 启动直接崩溃
（`exited code=1`），服务彻底不可用**。

修复要点（见 `polish.sh` 注释）：

1. **备份时机**：只有当前 profile **尚未注册本插件**时才备份，
   否则跳过，避免备份出「已污染」的配置。
2. **回滚顺序**：先让 profile 不再引用本插件，**最后**才删文件。
3. **幂等兜底**：无论是否成功恢复备份，都再执行一次 `unregister_bundle`。
4. **结果校验**：`revert` 结束后检查 profile 是否仍残留引用，残留则以非零码退出。
5. **状态告警**：`status` 会明确标出「bundle 已注册但目录不存在」这一会
   导致 dsh 崩溃的危险状态，并统计「干净可用备份」数量。

端到端回滚验证（4/4 通过）：

```
--- 步骤1：回滚 ---        ✅ 已从干净备份恢复 + 摘除 + 删除 + 重启
--- 步骤2：profile 残留 --- ✅ 无残留
--- 步骤3：服务存活 ---     ✅ bridge:3000 → 401（正常鉴权响应）
--- 步骤4：插件目录 ---     ✅ 已删除
```

`revert` 后 `dsh-mobile-polish` 从 `dependencies` 与
`dsh.profile.bundles` 中完全消失，其余插件
（`dsh-mobile`、`dsh-local-loopback-trust`）不受影响。

### 10.6 已知限制

1. **只覆盖聊天消息区 + 底部输入区** —— 侧边栏、设置面板、插件面板未做移动端适配。
2. **不改变布局结构** —— 原生把时间戳放在 `xzv4MW_actions` 容器内，
   只能靠 `order: -1` 调整其出现位置，无法真正「移进气泡内部」。
3. **依赖 hash 类名的子串** —— 若上游大改类名规则（例如去掉 `_` 前缀），
   选择器会**静默失配**，页面回落到原生样式（不报错）。
4. **`color-mix()` 需较新浏览器** —— Safari < 16.2 / Chrome < 111 不支持，
   竖线颜色会回落默认值（不影响布局）。
5. **v8 的 JS 补丁依赖 dsh 原生侧栏结构** —— 它监听会话行点击后调用原生
   遮罩的 `click()`。若上游改为渲染 `.dshm-drawer`，原生 handler 会自行生效，
   本补丁因「检测到侧栏已收起就不动作」而自动让位，不会重复关闭。
6. **【v12 新发现】滚动到底部时，悬浮的「⌄ 回到底部」按钮会与输入框、时间戳
   视觉重叠** —— 该按钮是原生绝对定位元素，此前被宽松的行间距「藏」住；
   v12 压紧间距后它显露出来。属原生层级 / z-index 设计问题，本插件不改结构，
   暂不处理。若需修，需给该按钮加 `bottom` 偏移或 `z-index` 调整。

#### 10.6.1 v8 **未修复**的两个问题（环境限制，非前端缺陷）

用户反馈的 5 个问题中，**#3 文件服务不可用** 与 **#4 打开配置文件失败**
未修复，因为根因不在前端，而在沙箱环境：

## 十一、已知限制

1. **dsh 处于 developer preview** —— `0.1.5-rc.1` 为预发布版本，API
   「will continue to evolve rapidly」，插件与宿主的契约可能随版本变化。

2. **移动端插件资源走独立链路** —— `dsh-mobile` 的静态资源设计上只服务
   loopback 的手机 App / 局域网场景。公网 Web 前端拿到的是桥接层补齐的等价响应，
   移动端的完整能力（配对、设备管理、远程通道）需通过插件自己的网关使用。

3. **token 随重启轮换** —— 每次重启服务都会生成新 token。已换取到 Cookie
   的浏览器不受影响（Cookie 有效期 30 天），但重新分发的带 token 链接会失效。

4. **依赖边缘 CDN 行为** —— 沙箱前置有边缘 CDN，服务未就绪期的 404 可能被短暂缓存。
   排障时可加唯一查询串（`?cb=<random>`）绕过缓存。

5. **网关 Host 需运行时学习** —— 预热实例阶段 `X_IDE_SPACE_KEY` 可能与实际网关
   空间键不一致，无法静态推导。桥接已做学习 + 持久化，但**首次部署时**
   第一个请求会触发一次 dsh 热重启（约数秒）。

6. **Settings 依赖安全边界放宽** —— 公网域名下 Settings 之所以可用，是因为
   `dsh-local-loopback-trust` 注入了 `ownsHost: true`（见[坑 7](#坑-7settings-面板报加载提供方目录失败)）。
   这**绕过了 dsh 官方一道有意的安全边界**，等价于把 settings 文档（含凭据字段）
   开放给所有能访问该 URL 的人。若该 URL 的访问控制不够可靠，
   应把插件的 `enabled` 改为 `false` —— 代价是公网下 Settings 面板变为不可用
   （其余功能不受影响），此时可改用端口转发访问 `127.0.0.1:13080` 来修改设置。

7. **本地方案作为兜底** —— 如需在**完全不放宽安全边界**的前提下修改模型设置，
   可建立 SSH 端口转发后访问 `http://127.0.0.1:13080/`：
   loopback 地址天然满足 `isLoopbackHostname`，`persistence` 取 `"host"`，
   Settings 全功能正常，无需任何插件介入。

## 附录 A：核心代码解析

### A.1 请求处理总入口

```js
const server = http.createServer((req, res) => {
  pickHost(req);                                    // 学习网关 Host

  // ① open-in-app 图标补全（无桌面环境）
  if (req.url.startsWith('/open-in-app/icon/')) {
    if (handleOpenInAppIcon(req, res) !== false) return;
  }
  // ② dsh-mobile 静态资源补齐（插件独立网关只服务 loopback）
  if (req.url.startsWith('/mobile-access/') || req.url === '/mobile-access') {
    if (handleMobileAccess(req, res) !== false) return;
  }
  // ③ 其余全部转发给 dsh
  proxyHttp(req, res);
});
```

设计要点：补全函数返回 `false` 表示"未处理"，请求继续走转发 ——
这样**未准备资源的路径自然落回上游**，保持其原本语义。

### A.2 Host 学习与持久化

```js
const learnedHosts = new Set(loadKnownHosts());   // 启动时载入历史
const activeTrusted = new Set();                  // dsh 当前生效的信任列表

function pickHost(req) {
  const host = req.headers.host;
  if (!host) return;
  traceReq(req);
  if (/^(127\.0\.0\.1|localhost|\[::1\])(:\d+)?$/i.test(host)) return;  // 平台探测无学习价值
  if (learnedHosts.has(host)) return;
  learnedHosts.add(host);
  saveKnownHosts();                               // 落盘，下次启动直接可用
  console.log(`learned gateway host: ${host}`);
  if (dshProcess !== null && !activeTrusted.has(host)) restartDshWithNewHost();
}
```

**为什么持久化很重要**：早期版本每次都靠热重启纳入新 Host，
重启窗口内网关健康检查失败可能**摘掉后端**，造成服务抖动。
持久化后启动时直接带上，**重启次数降为 0**（实测确认）。

### A.3 dsh 启动时序

```js
server.listen(PORT, '0.0.0.0', () => {
  // 先打印就绪日志 —— 平台探测窗口只有约 5 秒
  console.log(`serving http on 0.0.0.0:${PORT}`);
  console.log(`listening on port ${PORT}`);

  // 再等首个外部请求学习 Host（超时兜底，避免空等）
  let started = false;
  const kickoff = (reason) => {
    if (started) return;
    started = true;
    startDsh();
  };
  const poll = setInterval(() => {
    if (learnedHosts.size > 0) { clearInterval(poll); kickoff('learned gateway host'); }
  }, 100);
  setTimeout(() => {
    clearInterval(poll);
    kickoff(`timeout after ${LEARN_TIMEOUT_MS}ms`);
  }, LEARN_TIMEOUT_MS);
});
```

**顺序很关键**：平台的就绪探测窗口约 5 秒，窗口内探测命中
`/serving http/i`、`/listening on/i` 等关键词才认为服务就绪。
所以必须**先监听端口并打印日志，再启动 dsh**。

### A.4 WebSocket 升级转发

```js
server.on('upgrade', (req, socket) => {
  pickHost(req);
  const headers = forwardHeaders(req);
  const upstream = http.request({ hostname: DSH_HOST, port: DSH_PORT,
                                  path: req.url, method: req.method, headers });
  upstream.on('upgrade', (upRes, upSocket, upHead) => {
    const lines = [`HTTP/1.1 ${upRes.statusCode} ${upRes.statusMessage}`];
    for (const [k, v] of Object.entries(upRes.headers)) lines.push(`${k}: ${v}`);
    socket.write(lines.join('\r\n') + '\r\n\r\n');
    if (upHead && upHead.length) socket.unshift(upHead);
    upSocket.pipe(socket);
    socket.pipe(upSocket);
  });
  upstream.on('error', () => socket.destroy());
  upstream.end();
});
```

`/api/remote.mux` 是 WebSocket 长连接，承载实时通信。必须单独处理 `upgrade`
事件，否则前端实时能力全部失效。
