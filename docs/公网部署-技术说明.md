把 dsh 的 Web UI 通过沙箱网关暴露为公网 HTTPS 地址的完整方案与排障记录。

## 二、为什么需要一层桥接

dsh 官方**明确禁止**绑定 `0.0.0.0`：

```
error: --host 0.0.0.0 is intentionally not supported yet for safety:
it would expose remote code execution to the network; use 127.0.0.1 instead
```

这是安全设计——dsh 能执行任意代码，暴露到网络等于开放 RCE。所以只能：

```
公网域名（CLB 做 TLS 终止）
  → 沙箱网关
  → dsh-public-bridge.js（0.0.0.0:3000，承接外部流量）
  → dsh web（127.0.0.1:13080，只信任本机）
```

`dsh-public-bridge.js` 同时承担 TCP 转发、WebSocket 升级转发、Host 头透传。

## 三、踩过的六个坑

### 坑 1：进程模型 —— `&` fork 的后台进程不被代理

平台**只代理「自启动命令直接子进程」监听的端口**。脚本里用 `nohup ... &` 起的后台进程，
即使端口在监听，公网照样 404。

**对照实验**

| 启动方式 | 公网可达 |
|---|---|
| `node server.js`（前台） | ✅ |
| `bash script.sh`（内部 `&` 起服务） | ❌ 404 |

**解法**：桥接脚本必须前台常驻，dsh 作为它的 `spawn` 子进程。

### 坑 2：Host 头 —— 改写即 401 死循环

dsh 的会话 Cookie 以 **Host（authority）绑定**：

```js
function cookieName(authority) {
  return COOKIE_PREFIX + encodeBase64Url(sha256(authority));
}
// 校验时要求 cookie payload 里的 authority === 当前请求的 authority
```

早期版本的桥接把 Host 强制改写成 `127.0.0.1:13080`，导致公网域名下的 Cookie
永远校验失败 → 反复 401。

**解法**：**原样透传 Host**，只补 `X-Forwarded-*`。

### 坑 3：`/api` 403 —— browser-trust fence

dsh 对 `/api` 有一道额外的信任校验：

```js
function isTrustedApiRequest(request, trustedHosts) {
  const hostUrl = parseAuthority(request.headers.host);
  if (!isLoopbackHostname(hostUrl.hostname) && !isTrustedAuthority(hostUrl, trustedHosts))
    return false;   // → 403
  ...
}
```

而**网关转发时会把 Host 改写成沙箱内部域名**：

```
<PORT>-<SPACE_KEY>.e2b.<REGION>.sandbox.cloudstudio.club
例：3000-<YOUR-SPACE-KEY>.e2b.bj7.sandbox.cloudstudio.club
```

这个内部域名**不在** `--trusted-host` 里，于是 `/api` 恒 403（首页 200，因为它不走这个校验）。

**难点**：`SPACE_KEY` **不等于**进程环境变量 `X_IDE_SPACE_KEY`——平台注入的是预热实例
的 ID（如 `warm-accc118e-...`），与网关实际使用的值不一致，**无法静态推导**。

**解法 1**：运行时从首个到达的请求上**学习** Host，学到新 authority 时**热重启 dsh**
把它纳入信任列表。后来进一步改为持久化到 `.known-hosts.json`，启动时直接带上，
把重启次数压到 **0**，避免热重启窗口内网关健康检查失败摘后端。

**解法 2（更隐蔽，静态资源已然 200 却 API 全 403 的真凶）**：
`isTrustedApiRequest` 的后半段是

```js
if (header(request.headers, "sec-fetch-site") === "cross-site") return false;
const origin = header(request.headers, "origin");
if (origin === undefined) return true;
return new URL(origin).host === hostUrl.host;   // ← 卡在这里
```

网关把 **Host** 改写成内部域名，但浏览器发出的 **Origin** 仍是用户访问的**公网域名**，
两者 authority 不等 → 恒 403。浏览器对 POST 必然发送 `Origin`，所以这不是边缘情况。

**解法**：桥接层在转发时把 `Origin` / `Referer` 一并重写为与 `Host` 同一 authority，
让上游看到的一组头自洽（真实浏览器在公网域名下访问时，这两者本就应该相等）。

### 坑 4：移动端资源 404 —— 插件网关只监听 loopback

dsh-mobile 0.4.1 把 `/mobile-access/*` 静态资源挂在它自己的「独立网关」上，而该网关的
配置（见插件 `cordis.patch.yml`）是：

```yaml
initiallyEnabled: false
listenHost: 127.0.0.1
listenPort: 3443      # 实际运行时被模板改写为 0，即随机端口
allowedCidrs: [127.0.0.0/8]
```

它**只服务 loopback 上的手机 App / 局域网场景**，永远不会出现在面向公网的主 web 端口上，
所以前端加载时必然拿到 404。

**排除的误判**：一度以为「启用插件」即可解决，实测确认无效——
即使写入 `control.json` 让 `enabled: true`，该网关仍只绑 loopback 随机端口。
同时确认插件的**管理 API** `/api/mobile-access/*` 已正确挂载到主服务
（返回插件自身 JSON 的 `{"error":"forbidden"}` 而非 404），说明装配本身没问题。

**解法**：在桥接层按插件**自身语义**补齐这 4 个响应：

| 路径 | 响应 |
|---|---|
| `/mobile-access/custom.css` | 200 + `CUSTOM_STYLE_FALLBACK` 常量内容 |
| `/mobile-access/custom.js` | 200 + `CUSTOM_SCRIPT_FALLBACK` 常量内容 |
| `/mobile-access/extensions/manifest` | 200 + protocol 1 结构（`extensions: []`） |
| `/mobile-access/extensions/events` | 200 + SSE 长连接 |

内容取自插件源码里的常量与响应结构，**不是凭空伪造**——与插件独立网关在未配置自定义内容时
的响应完全等价。客户端本就有 `handleMissingExtensionManifest` 降级分支，补齐只是让控制台干净。

### 坑 5：open-in-app 图标 404 —— 无桌面环境提取不到图标

`/open-in-app/apps` 返回 `{"apps":["filemanager"]}`，前端据此去取
`/open-in-app/icon/filemanager`，但上游返回 404 JSON：

```json
{"code":"not-found","message":"no icon for filemanager"}
```

**原因**：dsh 的 open-in-app 在 Linux 上从系统 `.desktop` 文件**提取**真实 PNG 图标
（见 `@deepseek-ai/dsh-host-open-in-app` 的 `iconOf` / `extractAppIcon`）。
沙箱是无桌面环境，`filemanager`（依赖 `xdg-open`）能探测到启动器，
但图标提取失败，于是上游**主动**返回 404。源码注释写明这是既定语义：

> a 404 here means detection didn't find that launcher

**影响**：图标在客户端只用于 `<img src>`（`iconUrl()`），是**纯装饰性**资源。
按钮点击走 `POST /open-in-app/open`，与图标无关，功能零影响。

**解法**：桥接层为**已确认可用的应用**补一个语义对应的文件夹图标
（`icons/filemanager.png`）。刻意不做全局兜底 ——
未准备图标的 id 仍落到上游，保持其原本的 404 语义。

### 坑 6：端口注入 —— `PORT=8089` 必然 EADDRINUSE

平台自启动时会注入 `PORT=8089`，但 **8089 已被沙箱内置的 `sync_server` 占用**：

```
Error: listen EADDRINUSE: address already in use 0.0.0.0:8089
```

且平台用的 Node 是 **v22.13.1**（`dsh` 需要 v24，见下），
`import.meta.main` 在 v22 下为 `undefined`，会让 dsh CLI 静默失效。

**解法**：桥接脚本**忽略平台注入的 `PORT`**，固定用 3000；
dsh 用**绝对路径** `/root/.nvm/versions/node/v24.20.0/bin/dsh` 拉起，规避运行时版本差异。

## 四、部署命令

```bash
node "/root/.codebuddy/skills/发布为应用/scripts/publish.js" \
  --dir /workspace \
  --port 3000 \
  --language node \
  --install-cmd "" \
  --start-cmd "node /workspace/dsh-公网部署/dsh-public-bridge.js"
```

发布脚本会：写入平台自启动配置 → 探测本地端口就绪 → 调用 agentos 发布接口
→ 返回分享链接。

## 五、已知现象

### 边缘 CDN 缓存 404

平台域名前有 CDN（响应头 `eo-cache-status`）。**服务未就绪期间产生的 404 会被缓存**，
即使服务已恢复，不带查询串的请求仍可能命中旧缓存。

临时绕过：`https://<域名>/?t=123456`（唯一查询串）。

### 路由同步延迟

发布接口返回 `status: AVAILABLE` 后，公网域名生效仍需数十秒。刚发布完立刻访问
可能得到网关的 `404 page not found`（19 字节，`server: CloudStudio Gateway`），
等待片刻即恢复。

### token 每次重启都会变

dsh 的启动 token 由 `randomBytes(32)` 生成，每次进程启动都不同。
桥接脚本会捕获它并写入 `/workspace/dsh-公网访问地址.txt`。
首次访问带一次即可，之后浏览器持 Cookie（约 30 天）即可免 token。
